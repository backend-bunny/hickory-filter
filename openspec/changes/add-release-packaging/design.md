# Design

## Context

See proposal.md for the motivation and specs/ for the required behaviour. Constraints that shape the approach:

- Wolfi, which the runtime image uses, ships Rust toolchains (`rust-1.xx`) that target glibc only. It has no musl Rust target. A static *glibc* build would link LGPL-2.1 code into the binary, with relinking obligations. musl is MIT.
- Alpine's `rust` targets musl natively. `-C target-feature=+crt-static` gives a static-pie binary.
- apko's SPDX SBOM lists APKs, not the crates compiled into a binary.
- Keyless cosign and SLSA provenance need a CI with an OIDC token issuer. Repo hosting is still open (AGENTS.md), so paths use `<registry>/<owner>`.

## Goals / Non-Goals

**Goals:**
- One script set for local builds and CI (`hack/*.sh` + a task runner), with tools from one pinned manifest.
- A build of a given commit installs exactly the reviewed runtime package set and the locked crates.
- Image and chart verifiable from their digests alone (signature + attestations).

**Non-Goals:**
- Multi-arch images (x86_64 only, until a consumer needs more).
- A source-archive OCI artifact (corresponding source stays the tagged commit plus the crates' registry sources listed in the notices).
- Admission-policy manifests for consumers; the chart README documents the verification commands instead.
- Automated dependency-update tooling and lock-refresh schedules (a later change).

## Decisions

### D1. Build on Alpine, run on Wolfi
melange's build environment uses Alpine's main and community repositories (a pinned stable branch, signed by Alpine's key): `build-base`, `rust`, `cargo`, `cargo-auditable`, `busybox`, `ca-certificates-bundle`. It sets `RUSTFLAGS="-C target-feature=+crt-static"` and builds with `--target $(uname -m)-alpine-linux-musl`, so build scripts and proc macros stay host-dynamic while the binary is static. The runtime image is assembled by apko from Wolfi: `hickory-filter@local` + `ca-certificates-bundle`.
- *Why:* static musl gives no libc in the image and no LGPL code in the binary, and keeps the image minimal. Wolfi for runtime keeps a locked, regularly patched base for the CA bundle and layout.
- *Alternatives:* Wolfi static glibc (LGPL relinking obligations; NSS/DNS quirks in static glibc); `cargo zigbuild` or `cross` (an extra toolchain outside melange's environment, and harder to record in the SBOM); a rustup-installed musl target in the build (a network download during build, so not offline and not in the SBOM).
- *Consequence:* the release compiler is Alpine's `rust` version for the pinned branch. `rust-version` in `Cargo.toml` is set to it. Development may use a newer toolchain (`rust-toolchain.toml`), but CI also builds with the release compiler, through melange, so code must compile on it. `hickory-server`'s own minimum Rust version must not exceed it. Check this on every hickory bump.
- The test pipeline runs in a Wolfi environment (`binutils`, `busybox`) and asserts no program interpreter and no `NEEDED` entries (`readelf`). It runs the binary there, which proves it doesn't depend on Alpine's musl.

### D2. Offline, locked compilation from vendored crates
`hack/build.sh` copies committed files into a temp source dir and runs `cargo vendor --locked --versioned-dirs`, writing the `.cargo/config.toml` source replacement. It passes the directory to `melange build --source-dir`. melange runs `cargo auditable build --locked --release --offline`.
- *Why:* compilation sees exactly `Cargo.lock`'s crates, and the same vendored tree feeds notices generation (D5).
- `CARGO_TARGET_DIR` points at melange's cache mount, so CI can persist it.

### D3. apko lockfile and throwaway melange key
- `apko.lock.json` is committed and generated by `hack/lock.sh`. It holds Wolfi packages only. The `@local` hickory-filter APK changes its control hash on every commit, so `hack/lockfile.py merge` adds it at build time and fails when the committed lock and a fresh resolve disagree on the Wolfi set.
- Each build runs `melange keygen` in a temp dir, signs the APK, deletes the private key, and passes the public key to apko with `--keyring-append`. The key is never listed in `apko.yaml`.
- `melange test` and apko get no package cache, so they always install the just-built APK.

### D4. Release pipeline (tag → artifacts)
```
vX.Y.Z tag
  └─ check versions (tag = Cargo.toml = melange = chart)
  └─ cargo fmt/clippy/test, cargo deny check licenses
  └─ chart lint + schema validation (default + all-optional values)
  └─ build (D1–D3) → image tar + SBOMs + notices
  └─ image smoke test
  └─ apko publish → tags X.Y.Z, sha-<short> → resolve index digest
  └─ cosign sign index; attest SPDX SBOM; attest notices; SLSA provenance
  └─ package chart with image.digest = index digest → helm push (OCI)
  └─ cosign sign chart digest; SLSA provenance for chart digest
  └─ append digests + verify commands to the release notes
```
- The digest is resolved from the pushed tag (the index), never from apko's per-arch image refs, so signatures sit where the tags point.
- The chart is packaged from a temp copy with `image.digest` filled in. The committed `values.yaml` keeps `digest: ""`.
- Versioning: a release PR tool bumps `Cargo.toml`, `melange.yaml` and `Chart.yaml` together. The exact tool is picked during implementation, and `hack/check-version.sh` enforces the invariant whichever tool is used.
- Permissions: workflows default to `contents: read`. Only the release job gets `packages: write`, `id-token: write`, `attestations: write` (and `contents: write` for release notes). PR CI runs build + tests + a publish dry run without those permissions, and no `pull_request_target`.

### D5. License notices: generated from the vendored tree, shipped twice
`hack/notices.py` (Python standard library only) reads `cargo metadata --locked --filter-platform <musl target>`. It walks normal dependencies from the binary's package, and for each crate reads its declared license and every top-level file matching `licen[cs]e|copying|notice|copyright|unlicense` from the vendored sources (D2). Canonical SPDX texts, from a pinned commit of the SPDX license-list data, fill crates that ship no file. musl's license comes from the build environment's musl package. Output: `notices.json` (attestation predicate, project-defined type `…/hickory-filter/notices/v1`) and `THIRD-PARTY-NOTICES.md`. The Markdown goes into the source dir before melange runs and is installed into `/usr/share/doc/hickory-filter/` with the project `LICENSE`.
- *Why both:* a static binary distributes the crates. Shipping the notices *with* the image keeps the obligation satisfied even when the image is copied without its attestations. The attestation keeps them machine-verifiable on the digest. Size is small (a few hundred KiB of text).
- *Allowlist:* `cargo deny check licenses` with `deny.toml` (permissive licenses, e.g. MIT, Apache-2.0, BSD-2/3-Clause, ISC, Unicode-3.0, Zlib, MPL-2.0 file-level). It runs in CI and in the release job.
- *Alternative:* `cargo about` (template-driven). Viable, but one more pinned tool. The script also handles the reviewed-exception list and the musl entry.

### D6. Helm chart layout
`charts/hickory-filter/` with `values.schema.json` (fails on unknown or invalid values), templates for Deployment, Service, ConfigMap, ServiceAccount, and opt-in PDB, NetworkPolicy and ServiceMonitor.
- The config is rendered from `values.config` (a map, serialised to TOML), or read from `existingConfigMap`. A `checksum/config` annotation rolls the pods on change.
- The security context defaults meet `restricted` Pod Security. `/tmp` is an `emptyDir`, and the cache is an optional `emptyDir` or PVC.
- Service: `port: 53` → `targetPort: 1053`, UDP and TCP, plus an HTTP port for metrics.
- Validation: `helm lint` and a Kubernetes schema validator (pinned) over default and `ci/all-on-values.yaml` renders. In the image smoke test the chart isn't installed; cluster install is checked with a kind-style test only if added later.

### D7. Pinned toolchain manifest
One manifest (a devbox-style `devbox.json` + lock) pins melange, apko, cosign, helm, the schema validator, cargo-deny, bubblewrap, python3, jq and the dev Rust toolchain. CI installs tools from it, and Taskfile tasks call the same `hack/` scripts.

## Risks / Trade-offs

- [The Alpine build environment isn't locked like the apko runtime] → Pin a stable Alpine branch (fixes only). melange's SBOM records the installed build packages. Bump the branch as its own reviewed change.
- [Alpine's rust lags behind stable, and hickory's MSRV may overtake it] → Check on every hickory bump (D1 consequence). If blocked, wait for the next Alpine branch, or revisit the alternatives in D1.
- [musl's allocator is slower under high QPS] → Benchmark in the first change's task 4.3 on the musl build. If it matters, use a pure-Rust or bundled allocator crate (adds a dependency, statically linked, still no libc).
- [musl DNS resolver differences] → hickory-filter resolves upstreams by IP and list hosts through `hickory-resolver` (D4 of the first change), so musl's `getaddrinfo` is mostly bypassed. The system-resolver fallback reads `/etc/resolv.conf` directly, which works in pods.
- [The chart and image go out of step] → The chart is only published in the same release run, with the digest just pushed.
- [Notices miss a crate] → Generated from the same `cargo metadata` and vendored tree as the build. A test compares the notices' crate list with cargo-auditable's embedded list in the binary.

## Migration Plan

New project, nothing to migrate. AGENTS.md already carries the packaging rules; task 1.1 reconciles them with the implementation. The first tag publishes the first image and chart.

## Open Questions

- Release PR tooling (D4). It doesn't change the specs, and `hack/check-version.sh` enforces the invariant either way.
- Registry and owner paths, which follow from the repo hosting decision (AGENTS.md). They don't change behaviour.
